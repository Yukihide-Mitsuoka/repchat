# Spike: WrenAI 評価

LOG-0066 が「効くのは定義層であって生成ではない」を実測したあと、**その定義層を自分で発明する前に**、
既存のオープンソースを評価しました。`spikes/report-generation/metrics.json` は、
**MDL の劣化版を作り始めている状態**だったためです。

対象は **WrenAI**（Canner、`pip install wrenai`、評価時 0.13.1 / wren-core-py 0.7.2）。

## 分かったこと（要約）

| 論点 | 結果 |
|---|---|
| Git管理できるか | ✅ **できる**。MDL は YAML ファイル群、接続情報は `~/.wren/profiles.yml` に**分離** |
| 導入の重さ | ✅ `pip install` のCLI。**Docker不要** |
| セマンティック層 | ✅ models / relationships / views / cubes / knowledge |
| NL→SQL を持つか | ❌ **持たない**。LLMは呼ばず、**エージェントがCLIを駆動**する設計 |
| **GA4 の生エクスポートに使えるか** | ❌ **そのままでは使えない**（後述） |
| アクセス制御 | ⚠ README は RLAC/CLAC を謳うが、**アーキテクチャ文書にもMDLリファレンスにも記載なし** |
| マルチテナント | ⚠ **記載なし**。構造は「1プロジェクト＋1アクティブプロファイル」のCLI |

## Git 管理は失われない

これが最初の関心事でした。**MDL はプロジェクト配下の YAML です。**

```
wren_project.yml            models/<name>/metadata.yml   relationships.yml
views/ cubes/               knowledge/{rules,metrics,glossary,caveats,sql}/
target/mdl.json             # コンパイル済み。エンジンが読む
~/.wren/profiles.yml        # 接続情報。プロジェクト外＝Gitに入らない
```

ロールバック・ブランチ切り出し・Actions での検証は通常の Git 操作で成立し、
**Secrets はリポジトリ外**に分離されています。**Git を諦める必要はありません。**

## LLM は持っていない — これは利点

`wren ask` は薄いラッパーで、「あなたは wren CLI を使える」と問いを添えるだけでした。
**意味層・SQL計画・コネクタを提供し、LLMは呼ばない**設計です
（`knowledge/` の収集も、エージェントが `wren context instructions` 等を叩いて行う）。

つまり **既存の Gemini パイプラインをそのまま使えます。** 置き換えではなく、下に敷けます。

## GA4 では、そのままでは使えない

`ref_sql` に書いた SQL は wren-core 自身のパーサを通ります。切り分けた結果:

| `ref_sql` 内の構文 | 対応 | 備考 |
|---|---|---|
| バッククォート識別子 `` `a.b.c` `` | ❌ | `Expecting )` でパース失敗 |
| **相関 `UNNEST` サブクエリ** | ✅ | **通る。** 当初の懸念は外れ |
| **ワイルドカードテーブル `events_*`** | ❌ | `Expected: end of statement, found: *` |
| `table_reference`（構造化指定） | ✅ | 正しく展開される |

**GA4 のエクスポートは日次シャードで、月次レポートは `events_*` ＋ `_TABLE_SUFFIX` が前提**です。

### 追試で、理由を訂正しました（2026-07-28、LOG-0068）

初版は「**ワイルドカードが致命傷**」と書きましたが、**不正確でした**。ワイルドカードは
`table_reference` に `table: events_*` と書けば通ります。しかも生成される
`` `bigquery-public-data`.dataset.`events_*` `` という分割バッククォートは、
**BigQuery で実際に動きます**（1日分 22,096 行を確認済み。計画が通ることと動くことは別なので実行した）。

正しくは、**1つのMDL構文の中でワイルドカードと平坦化を両立できない**、です。

| | ワイルドカード | UNNEST 平坦化 |
|---|---|---|
| `ref_sql` | ❌（引用符の有無を問わず） | ✅ |
| `table_reference` ＋ 計算列 | ✅ | ❌ |

計算列に `UNNEST` の相関サブクエリを書くと、意味エンジンが式中の識別子をモデルの宣言列に対して
解決しようとし、**`key` / `value` が見つからず失敗**します（`source column not found: key`）。
**UNNEST の中身が見えない**ためで、`event_params` を宣言しても解消しません。

**結論は変わりません** — GA4 の平坦化は MDL の外（BigQuery のビュー）に置く必要があります。
変わったのは理由の精度です。

### 回避策と、その代償

**BigQuery 側にビューを作り、`table_reference` をそこへ向ける。** 動きますが、
**顧客のプロジェクトにビューを作る権限が要ります**。これは
[ADR-0010](../../docs/adr/0010-connection-identity-is-never-a-person.md) D1 の
**読み取り専用のテナント別サービスアカウント**と衝突します。書き込み権限を足すか、
顧客側に作ってもらうか、どちらも設計判断です。**採用の前に決める必要があります。**

## アクセス制御は、預けられる状態にない

README は RLAC/CLAC を挙げますが、**アーキテクチャ文書にも MDL リファレンスにも記載がありません**。
リファレンスで確認できるのは「モデルに露出しない列は物理的に見えない」だけです。

ADR-0010 D6（**制御はドリフトしたときにどちらへ倒れるかで採否を決める**）に照らすと、
**文書化されていない制御に境界を預けることはできません**。自前を維持する理由が、懸念ではなく事実になりました。

## Apache 2.0 での大幅改修について

**法的には問題ありません。** 改変・再配布・商用利用が可能で、改変部分を非公開のまま SaaS
として提供できます（ネットワーク・コピーレフトが無いため）。義務はライセンス全文の同梱、
著作権・帰属表示の保持、**改変ファイルへの変更明記**（§4b）、NOTICE があればその引き継ぎ。
特許許諾も付きますが**特許訴訟を起こすと失効**します（§3）。

**商標は許諾されません**（§6）。Canner が "Wren" "WrenAI" とロゴを留保しているため、
**製品名に使えません**（COD-005 の表示専用方針と衝突しません）。

**実質的な制約は法務ではなく保守です。** リポジトリは **AGPL-3.0 を将来モジュール用に予約**しており、
公開パッケージは**マニフェストのライセンスが優先**します。採用するならバージョンを固定し、
更新時にパッケージ単位でライセンスを確認する運用が要ります。そして活発に開発中のものを
大幅改修すれば、更新を諦めるかリベースし続けるかになります。
**エンジンをフォークせず、依存として使い、周囲に自分の層を置く**のが妥当です。

## 再現手順

```bash
python3 -m venv .venv && ./.venv/bin/pip install "wrenai[bigquery]"
./.venv/bin/wren context init          # プロジェクト雛形
# models/ と knowledge/ を置き換える（このディレクトリの内容）
./.venv/bin/wren context build         # → target/mdl.json
./.venv/bin/wren dry-plan -s "SELECT ..." --connection-file conn.json
```

`conn.json` は `{"datasource":"bigquery","project_id":"…","dataset_id":"…"}`。
**`dry-plan` はDBに接続しない**ので、パーサの対応可否だけを安く確かめられます。

なお公式手順にある `curl … | bash` でのスキル導入は**行っていません**（外部スクリプトの直接実行を避けたため）。
CLI だけで評価は成立しました。

## この spike が答えていないこと

**同じ12問を投げた比較は、まだできていません。** GA4 を MDL に載せられないためで、
それにはビュー作成の権限問題を先に決める必要があります。
`spikes/report-generation` の測定値との直接比較は、その決定の後です。
