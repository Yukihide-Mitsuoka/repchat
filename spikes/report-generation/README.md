# Spike: レポート生成

[docs/positioning.md](../../docs/positioning.md) §5 が唯一残した関門を測ります。

> **今レポートを作っている人が、明日も作れるか。**

Looker Studio はドラッグ&ドロップで非エンジニアが作れます。こちらは「日本語で言う →
SQLが生成される → 人が承認する」で、**誰もSQLを書かないことが前提**です。その前提が成り立つかを、
**実データで**測ります。

## なぜ GA4 のエクスポートなのか

`bigquery-public-data.ga4_obfuscated_sample_ecommerce` は、**GA4リセラーの顧客が既に持っている
のと同じスキーマ**です（LOG-0064 の観測対象そのもの）。公開データなので顧客データを一切使いません。

そして**一番難しい形**でもあります。

- 「セッション」という行が**存在しない** — `user_pseudo_id` と `event_params` 内の
  `ga_session_id` の組を数える必要がある
- `event_params` は `ARRAY<STRUCT<key, value STRUCT<...>>>` で、`page_location` を取るだけでも
  `UNNEST` が要る
- `event_date` は `'YYYYMMDD'` の**文字列**
- `ecommerce.purchase_revenue` は `purchase` イベント行にのみ入る。`items` を `UNNEST` すると
  **二重計上**になる

[positioning.md §2.8](../../docs/positioning.md) は「**セマンティック層は選択肢ではなく必須**」と
述べています。その根拠は「生イベントからのセッション化は自然言語SQLが最も苦手な領域」という
予測でした。**この spike はその予測を検証します。** 通れば §2.8 は弱まり、落ちれば裏付けられます。
**どちらでも判断材料になります。**

## 測っていること

利用者の目的をVertex AIが分析仕様へ分解し、利用者が確定した仕様だけからSQLと可視化を生成できるかを
測ります。分析テーマ、指標、区分軸、グラフ種別、配置を登録済みの設問やパネル一覧から選びません。
GA4特有のnested/repeated構造、セッション化、購入金額の二重計上防止も生成SQLの検査対象です。

## 正しさの確かめ方

確定した分析仕様に対して、SQLの読取専用性、対象dataset、対象期間、出力列の別名・型・件数、行数上限を
BigQuery実行前に検査します。実行後も同じ描画契約で結果形状を検査し、不一致は描画しません。
手書きの参照SQLや登録済み設問との一致を成功条件にはしません。

## 出てくるもの

ローカル画面に、AIが考察した分析仕様、実際にBigQueryへ送ったSQL、取得データ、可視化、推定費用を
表示します。固定レポートを生成する実行経路はありません。

## 実行

既存スパイクと同じ venv を使います（`google-genai` と `google-cloud-bigquery` が入っています）。

```bash
gcloud auth application-default login
```

```bash
make demo-live PROJECT=kotonoha-bi-dev
```

スキャン量は `_TABLE_SUFFIX` で1か月に限定し、`maximum_bytes_billed` を 20GiB に設定しています。

## 結果（2026-07-27、gemini-3.5-flash、12セクション）

**9 / 12。1レポートあたり ¥1.36。** そして**落ち方が、予測と違いました。**

### SQLの機構は問題にならなかった

**§2.8 の予測は「生イベントからのセッション化は自然言語SQLが最も苦手」でした。外れています。**

`user_pseudo_id` と `ga_session_id` を組んだセッション定義、`event_params` の `UNNEST`、
`page_location` の取り出し、`purchase` 行に限定した売上（`items` の二重計上回避）、
ファネルのセッション串刺し、エンゲージメント時間の合算 —— **すべて正しく書けました。**
ファネル（R9）の数値も参照と完全一致です。

### 落ちたのは、定義が決まっていないところ

| | モデル | 参照実装 | 性質 |
|---|---|---|---|
| **R4 購入件数** | `COUNT(DISTINCT transaction_id)` = 895 | `COUNT(*)` = 1204 | GA4は同一取引で purchase が重複発火する。**モデルの方が妥当かもしれない** |
| **R10 新規判定** | `LOGICAL_OR(event_name='first_visit')` = 29527 | `ga_session_number = 1` = 28135 | **どちらもGA4の標準的な定義** |
| **R9 ファネル** | 縦持ち（3行） | 横持ち（1行3列） | 数値は完全一致。**表示形式の違い** |

**SQLが書けないのではなく、「購入件数とは何か」がデータの中に書かれていないだけ**です。

### 実行ごとに答えが変わる

`temperature=0` でも、**R4 は1回目・2回目が `COUNT(*)`、3回目が `COUNT(DISTINCT transaction_id)`**
でした。**同じ問いで、月によって購入件数が変わる**ことになります。月次レポートとしては失格です。

**これがセマンティック層が必須である本当の理由**です。難しいからではなく、**定義しないと安定しない**から。
[positioning.md §2.8](../../docs/positioning.md) の理由づけは、この結果に合わせて訂正しました
（LOG-0065）。

### 測定装置側の欠陥（初回の失敗3件のうち2件）

最初の実行では 9/12 でしたが、**うち2件はモデルではなく比較の作りが原因**でした。
「列名はモデルの自由」と書きながら、**グループ化のラベル文字列**（`新規` と `新規セッション`）と
**出力の列数**を自由として扱っていなかった。前者は `rows_unordered` を足し、後者は
**本番で既存レポートが列構成を決めるのと同じように、期待する形をプロンプトで伝える**ようにして解消。

もう1件（R5）は参照SQL側のタイムアウトでした。**例外メッセージが空**で診断できなかったため、
例外クラス名も記録するようにしています。

## 追試（2026-07-27）— 指標定義を渡すと安定するか

LOG-0065 の結論「定義しないと安定しない」は、**まだ仮定**でした。`metrics.json`（購入件数と
新規判定を含む最小の定義層）を渡して3回走らせ、比較しました。

この表は旧固定runnerで得た履歴です。runnerと入力fixtureは削除済みであり、現在のライブデモから
再実行する経路はありません。

| | 定義なし | **定義あり（3回）** |
|---|---|---|
| 検証通過 | 9/12 | **11/12（3回とも同じ）** |
| 購入件数 | **1204 ↔ 895 で揺れた** | **895 に固定** |
| 新規判定 | 29527 ↔ 28135 で揺れた | **28135 に固定** |
| **実行間で数値が同一** | いいえ | **12/12** |
| 実行間でSQL文面が同一 | — | **5/12** |

### 定義が固定するのは意味であって、構文ではない

**SQLの文面は12中7で実行ごとに変わっているのに、数値は12/12で一致しました。**
別名・整形・CTEの有無といった書き方は揺れてよく、**月次レポートに必要なのは数値の再現性の方**です。

**これが、セマンティック層に求められる要件を具体的にします。** 生成SQLをキャッシュして固定する
必要はなく、**定義を固定すれば結果は決まります。**

### 残る1件は「形」の問題で、定義層の守備範囲が足りていない

R9（ファネル）は3回とも同じ失敗です。**数値は 23105 / 4537 / 1115 で参照と完全一致**、
違うのは縦持ち（3行）か横持ち（1行3列）かだけ。しかも**毎回同じ選択**をしています。

`metrics.json` は**指標の意味**を宣言しますが、**出力の形**は宣言していません。
レポートとしてはどちらも正しく、**どちらで出すかは決めておかないと決まらない**。
セマンティック層は**指標の定義と出力形状の両方**を固定する必要があります。

## C5 の測定（2026-07-28）— 意図は成立、境界は誤り

ADR-0013 C5（**定義に無い語は生成せず問い返す**）は、起草時点で**唯一の未実測の決定**でした。
定義に**わざと入れていない**指標のセクションを3つ足し（R13 直帰率 / R14 平均滞在時間 /
R15 離脱率）、応答スキーマに `undefined_terms` を追加して測りました。

| | 結果 |
|---|---|
| **真に未定義**（R13 / R14 / R15） | **3/3 で拒否** |
| **言い換え**（R9 ファネル / R10 新規訪問） | **過剰拒否** |

**成立した側。** R14 が本命でした。「平均滞在時間」は未定義ですが、**定義済みの
「エンゲージメント時間」がすぐ隣にある**ため、代用したくなる設問です。**代用しませんでした。**

**誤っていた側。** 設問の「**新規訪問**」に対し、定義は「**新規セッション**」。モデルはこう答えました。

> ご指定の「新規訪問」および「リピート訪問」は指標定義に存在しないため、
> 定義済みの「新規セッション」「リピートセッション」で代用せず、未定義語として処理します。

**語の違いだけで拒否しています。** ファネル（「商品を見たセッション数」という説明的な言い回し）も同様。
しかも**実行ごとに揺れます** —— R7 は1回目に拒否され、2回目は通りました。

**判定基準が「意味が定義に解決できるか」ではなく「字面が一致するか」になっていた**ということです。
定義に**別名・言い換え**を持たせる必要があります。ADR-0013 C5 に補正を記録しました。

### 別名と合成規則を足した追試（同日）

LOG-0070 の過剰拒否は**2種類**あったので、分けて対処しました。

- **語の違い**（設問「新規訪問」／定義「新規セッション」）→ 定義に**別名**を持たせる
- **合成**（「商品を見たセッション数」＝セッション数を `event_name` で絞ったもの）→
  **「定義済みの指標を宣言済みの列で絞り込む・分割するのは代用ではない」**という規則を追加

| | run1 | run2 |
|---|---|---|
| 真に未定義（R13/R14/R15） | **拒否** | **拒否** |
| 言い換え・合成（R9/R10） | **回答** | **回答** |
| 合計 | 14/15 | **15/15** |

**両実行の差は R9 の「形」だけ**でした（縦持ち3行 vs 横持ち1行3列。数値はどちらも
23105 / 4537 / 1115 で正解）。**数値は安定し、残る不安定は出力形状に絞り込まれた** ——
これは **C4（出力形状も宣言する）が未実装だから**で、予測どおりの残り方です。

**過剰受容は起きませんでした。** `滞在時間` を「エンゲージメント時間」の別名に入れて
R14「平均滞在時間」と衝突させましたが、**両実行とも拒否**しています。別名は境界を緩めませんでした。

#### 正直に — 一部は循環している

`新規訪問` は**失敗した文字列そのもの**を別名に足しています。R10 が通ったのは当然で、
**測定として情報量があるのは R9（別名では解けず、合成規則で解けた）と、
R13〜R15（別名を足しても拒否が維持された）の方**です。

#### 別名の保守は顧客数に比例するか（D3の確認）

45個 / 12定義。**ただしこれは GA4 の語彙**で、GA4を使う顧客なら**同じものを使い回せます**。
標準化されたデータソースでは**顧客数に比例しません**。顧客固有の業務データを扱う場合は
別問題で、そこは未測定です。

## C4 の測定（2026-07-28）— 15/15 が2回、ただし過程に学びがある

ADR-0013 C4（**出力形状も宣言する**）を、セクションごとの `shape`（列の並びと行の単位）として実装しました。

| | 別名のみ | **形状のみ** | +引用符 | **表示名と別名を分離** |
|---|---|---|---|---|
| R9 ファネル | **揺れる** | 安定 | 安定 | 安定 |
| R8 / R11 / R12 | 通る | **壊れる** | 一部壊れる | 通る |
| 合計 | 14〜15 | 12 | 12〜13 | **15 / 15（2回）** |

**C4 の主張は成立します** —— 形状を宣言するとファネルの縦持ち／横持ちの揺れは止まりました。

**ただし宣言しただけでは3件が壊れました。** 宣言した列名を、モデルが**SQLの識別子として
そのまま使った**ためです。

- `AS 日付` → `Illegal input character "\346"`（非ASCII識別子は裸で書けない）
- `リピートユーザー率（％）` → **バッククォートで囲んでも** `Invalid field name`（全角括弧は不可）

**宣言は「表示名と順序」であって「SQL識別子」ではない。** 分離して初めて全部通りました。

これは Evidence の使い方とも一致します —— コンポーネントは `title` を data と別に受け取るので、
**表示名をSQLに埋め込む必要がありません。**

### そして4度目

`Invalid field name` が見えるまでに1往復無駄にしました。`exec_bq` が例外の**先頭200文字**を
返しており、BigQuery の `BadRequest` は**長いAPI URLから始まる**ため、
**エンドポイントだけが表示されて理由が隠れていた**のです。

例外から `errors[0].message` を取り出すよう直しました。**このセッションで4度目**の
「自分で診断情報を捨てる」で、いずれも同じ形 —— 出力を絞る・切る・握り潰す。

### ここでも、自分で診断情報を捨てていました

最初の実行では過剰拒否が `no sql` としか出ず、**生成失敗と区別がつきませんでした**。
`undefined_terms` と `reason` を記録するようにして、はじめて原因が読めました。
**このセッションで3度目**（空の bq エラー、`grep` で捨てたトレースバック、そしてこれ）。

あわせて**ADCのプリフライト**を入れました。期限切れが12セクション目でスタックトレースとして現れ、
**「何も出力されない」と誤読**していたためです（LOG-0056 で `deploy.sh` に入れたのと同じ考え方）。

## Evidenceで描画する手順（再現）

前提は Python 3.13以上、Node 18以上、git、npm、gcloud、ネットワーク接続、
BigQueryとVertex AIを使えるADCです。ADCが未設定なら、最初に一度だけ次を実行します。

```bash
gcloud auth application-default login
```

前提を満たした後は、リポジトリのルートで実行します。

| 用途 | コマンド |
|---|---|
| AIが考察するライブデモ | `make demo PROJECT=kotonoha-bi-dev` |
| 同じライブデモを明示して起動 | `make demo-live PROJECT=kotonoha-bi-dev` |

`demo-live`は`127.0.0.1:8765`だけで待ち受け、ダッシュボード、作成・編集、会議報告、単一グラフを
左ナビゲーションで切り替える分析ワークスペースを表示します。左ナビゲーションと右のパネル詳細は
個別に開閉でき、デスクトップでは境界のドラッグまたは左右矢印キーで幅を変更できます。ダッシュボードを
既定の成果物ビューとし、buildが完了したら作成・編集から自動で戻り、会議報告が生成されたら独立した
会議報告ビューへ移動します。狭い横幅では中央を優先して右詳細を初期状態で閉じます。対話履歴は
起動中だけ、Git連携は将来機能であり、永続化を模倣しません。

各送信で同じ指標定義、SQL安全検査、20GiB上限を使用します。生成・検査・実行・描画の段階、生成理由、
SQL、結果、Vertex AI推定費用をEvidence基調の画面に表示します。SQLは
GitHub Light相当の淡いコード領域で、予約語、関数、文字列、数値、コメント、識別子を色分けします。
SQL文字列はHTMLとして解釈せず、改行とスペースインデントを保持します。
分析計画、SQL生成、会議報告のusageは共通してprompt tokensを入力、candidate tokensとthought tokensの
合計を出力として費用換算します。thought token属性が無いSDK応答は0として扱います。この補正でモデル、
thinking level、生成回数は変更しません。
単一グラフの4段階とダッシュボードの3段階は、現在の段階を黄、完了済みを緑で表示します。
単一グラフと右のパネル詳細に表示するSQLの右上にはコピー操作を置き、成功・失敗をボタンの表示と
アクセシブル名で通知します。可視化内の件数は整数、率・売上などの連続値は最大小数2桁で表示しますが、
監査用の「取得データ」はBigQuery応答を丸めず保持します。Cloud費用の小数表示はこの規則の対象外です。

Bitcoinの実テーブル列`hash`はGoogleSQLの予約語です。生成SQLがCTEでこの列を裸の識別子として
再参照した場合だけ、文字列・コメント・修飾済み／引用済み識別子を保ったまま`` `hash` ``へ補正します。
画面には補正後の実際にBigQueryへ送るSQLを表示し、同じ補正を繰り返してもSQLは変化しません。

単一グラフ画面の分析対象では、GA4に加えてIssue #188の最初の非GA4プロファイルとして
`bigquery-public-data.crypto_bitcoin.transactions`を選択できます。画面の例題は、2024年1月の取引を
`outputs`、`output.addresses`の順に二段階で展開し、取引ごとの異なる受取アドレス数を4区分に分けて
取引数を棒グラフ化します。許可datasetはプロファイルIDからサーバー側で決め、ブラウザから任意の
project/dataset/table名を渡しません。`block_timestamp_month`が指定月の月初と一致しない生成SQL、
別dataset、`SELECT *`、DDL/DML、複数statement、100行超の結果はfail closedにします。

2026-08-02に基準SQLをBigQuery dry runし、処理見積りは3,115,504,440 bytes（約2.91GiB）でした。
dry runはデータ取得を実行せず、クエリ料金も発生しません。ライブ送信時は生成SQLの差を考慮して
20GiBをhard limitに保ち、画面で通常約¥4・最大約¥20を再確認します。基準SQLは再現用に
`bitcoin_profile.py`へ置きましたが、独立レビューも生成結果との実値照合も未実施です。したがってこの追加は
「公開された非GA4 nested/repeated schema 1種類でUIから経路を通せる」という縦切りに限り、
未知・非公開相当2種類の反復評価を求めるIssue #188は閉じません。

ダッシュボード生成は、まずVertex AIの分析plannerが1つの月次ECサイト分析目的を意思決定、仮説、
確認事項、KPI・グラフ候補へ分解します。最大3件の確認にはAIの推奨回答が採用済みで表示されるため、
変更がなければそのまま仕様を確定できます。回答欄を編集すると即時に採用状態へ反映され、空欄がある
場合だけbuildを停止します。「AIに再提案」は、現在選択している完全なpanel仕様と500文字以内の
追加・変更・削除依頼をAIへ戻す任意操作です。明示されていない既存panelは維持し、改訂時だけ
1〜`ANALYSIS_MAX_PANEL_COUNT`件を許可します。読者、比較軸、AIが新規に設計したパネルを編集した後に
仕様revisionをfreezeします。相談中はBigQueryを呼ばず、
確定後の別費用確認で初めてSQL生成とbuildへ進みます。仕様revisionと`demo-org-ec-v1`組織コンテキストrevisionは
生成ダッシュボードに表示します。生の会話をメモリーや認可判定には使用しません。
plannerのresponse schemaは`audience`、`comparison`、`business_goal`のうち未回答fieldだけを許可し、
全fieldが回答済みなら確認事項を0件へ制約します。schema制約に反する固定応答は後段でも拒否し、
エラーには実際のfieldを含めます。同じ相談を自動再試行しないため、Vertex AI呼出しは1回の操作につき
1回です。追加依頼なのに件数が増えないAI応答は拒否し、自動再試行しません。確定時にブラウザから返す
パネル情報は、AIが作った分析仕様を失わずそのままfreezeします。
単純問い合わせ、相談、報告のHTTP本文は最大4,096 bytes、確定分析計画は最大98,304 bytesとし、

## Evidence で実際に描画した（2026-07-28）

positioning §5 が「**次は設計ではなくデモ**」と書いていたのに、生成した markdown を
**Evidence でビルドして見た人がいませんでした**。通しました。

### 生成物を2つに分ける必要があった

**ページに BigQuery の SQL を直接埋めても動きません。** Evidence はソース定義
（`sources/<name>/*.sql`）でウェアハウスに問い合わせ、**ページSQLは自前の DuckDB 層**で
その結果を参照する設計だからです。ページに `_TABLE_SUFFIX` や `UNNEST` を書くと、
BigQuery ではなく DuckDB が解釈しようとします。

生成器を**2成果物**に変更しました。

```
out/sources/ga4/<id>.sql   # ウェアハウスSQL（BigQuery方言）
out/sources/ga4/connection.yaml
out/pages/monthly_report.md  # select <必要列> from ga4.<id> ＋ コンポーネント
```

**拒否されたセクションはソースファイルを作りません。** 定義漏れが、空のグラフに化けないためです。

### 認証は鍵不要だった

Evidence の BigQuery コネクタは **`authenticator: gcloud-cli`** で ADC を使えます。
**鍵ファイルが要りません。** WrenAI のコネクタが `credentials`（SA鍵）必須で D1 と衝突したのとは
対照的で（LOG-0068）、**Evidence を選んでいたことがここでも効いています**。

`npm run sources` で12本すべてが materialize（`r5 ✔ 6 rows` / `r7 ✔ 10 rows` /
`r8 ✔ 31 rows` など）、`npm run build` が通り、**実データで描画されました**。
