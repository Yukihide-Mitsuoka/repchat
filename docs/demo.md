# RepChatデモ — 5分説明

## 最初の30秒

RepChatは、分析担当者がLooker Studioでグラフを一つずつ作る代わりに、**日本語で書いた定期レポートの
要求を、チーム共通の指標定義に従うSQLとページへ変換する**仕組みです。分からない指標を推測で埋めず、
生成した数値を既知の正解と照合してからEvidenceのレポートとして表示します。

既存BIを置き換えること自体が目的ではありません。複数顧客へ同じ種類のレポートを提供する代理店や
ソフトウェアベンダーが、顧客ごとの手作業と担当者依存を減らすことが目的です。

## 5分で見せる順番

| 時間 | 見せるもの | 伝えること |
|---|---|---|
| 0:00–0:50 | 日本語1件から生成するダッシュボード | 具体的な月次分析依頼を、購入KPI、定着・エンゲージメント、ファネル、日次＋7日移動平均、回遊へ分解する |
| 0:50–1:40 | 生成された6つの分析パネル | ネスト集計やウィンドウ関数を含むSQLをパネルごとに生成し、1画面の読順へ配置する |
| 1:40–2:40 | 各分析の「生成プロセス・SQL」「集計データ」タブ | グラフに対応する生成SQL、生成理由、参照値照合、実クエリ結果を同じ分析内で確認する |
| 2:40–3:30 | 指標定義 | 「購入」「ユーザー」などの意味を代理店側で共通化し、顧客間で再利用する |
| 3:30–4:15 | 未定義指標の節 | 分からない語はもっともらしい数値を出さず、定義追加を求める |
| 4:15–5:00 | Looker Studioとの違いと限界 | 価値を確認し、未実装を製品機能として説明しない |

## Looker Studioとの違い

| 観点 | Looker Studioでの一般的な作業 | このデモ |
|---|---|---|
| レポート作成 | データ接続、計算フィールド、グラフを画面で個別設定 | 日本語の要求からSQL・ソース定義・ページを生成 |
| 指標の意味 | レポートや担当者ごとに計算式を持ちやすい | 代理店が共通の指標定義を保守し、生成時に必ず参照 |
| 曖昧な要求 | 作成者がその場で解釈する | 定義へ解決できない語は拒否し、定義追加を求める |
| 検証 | 作成者が目視や別集計で確認 | 生成フロー内で実行し、既知値と機械的に照合 |
| 成果物 | BIサービス内の設定 | 生成ページとソース定義を顧客のGitへ置く設計（ADR-0014） |

## この場で実測していること

- 日本語の15設問について、指標定義と出力形状を使った生成・実行・照合が**2回連続15/15**
- 定義していない3指標は推測せず拒否し、定義済み指標の言い換えと絞り込みは回答
- 12本のBigQueryクエリをEvidenceでmaterializeし、ビルドしたレポートの値が検証済みの値と一致
- 同じシェルへ2種類のデータを差し替え、再ビルドなしで別の値を表示できること

## 混ぜて説明してはいけないこと

このローカルデモは、**本番の認可ゲート、認証、executorを通りません**。したがって、この画面だけを
根拠に「テナント越境不能」とは言いません。テナント境界のfail-closedなSQL変換、認可ゲート、
ライブ配信は別の受入試験で実測済みですが、このデモと同じ経路にまだ統合されていません。

また、2テナント表示ではGA4の`device.category`を擬似テナントとして使い、12クエリ中2件だけを
差し替えています。実顧客のスキーマで非エンジニアが自力運用できるか、チームが用意した設問以外にも
精度が出るかは未測定です。

## 実演コマンド

ADC設定済みのリポジトリルートで実行します。実Vertex AIとBigQueryを使います。対面デモでは
参照値を登録済みの6問から、購入KPI、リピート率、平均エンゲージメント時間、購入ファネル、
日次セッションと7日移動平均、入口から3ページ目までの主要回遊を生成するショーケースを使います。

```bash
make demo PROJECT=kotonoha-bi-dev SHOWCASE=yes
```

Evidenceアプリの取得、依存関係のインストール、生成、照合、materialize、build、ブラウザ起動までを
含みます。詳細は[report-generation spike](../spikes/report-generation/README.md)にあります。
6問版は実Vertex AI・BigQueryで6/6、Vertex AI推定¥1.285、回遊12 edgeのSankey描画、
production build、ブラウザerror/warning 0まで確認済みです。

### 日本語をその場で入力するライブデモ

参加者が入力した日本語から、その場でSQL、グラフ、ダッシュボードを生成するローカルデモです。

#### 起動する

次のコマンドを実行します。

```bash
make demo-live PROJECT=kotonoha-bi-dev
```

起動時の費用確認後、`http://127.0.0.1:8765/`を開きます。このURLだけがボタン操作を受け付ける
ライブデモです。固定HTMLや画面検査用serverを参加者向けURLとして案内しません。APIがHTML、空body、
JSON以外を返した場合はHTML断片やJSON parser例外を表示せず、ライブデモへの接続を確認する案内を出します。

画面は一つの分析対話から成果物を作るワークスペースです。左paneはmode切替ではなく、ダッシュボード、
未保存のインサイト、会議報告と分析スレッドを分けた成果物treeです。中央下部の共通入力欄は通常時に同じ位置へ残り、
中央列が狭い場合はその幅へ追従します。中央列が広くても768pxを上限とし、通常カードより大きい22pxの角丸で
会話の入口だと判別できるようにしています。入力本文は内容に合わせて上方向へ伸長し、通常の長文では入力欄内に
縦スクロールを表示しません。送信前に次のactionを選びます。

- **ダッシュボード**: AIと分析計画を相談し、仕様確定後にbuildする
- **インサイト**: 単一グラフを生成し、未保存成果物として右paneで確認する
- **会議報告**: 最新のbuild済み根拠bundleから報告案を作る

左treeから保存済みまたはデモ上の成果物を選ぶと中央に本文を表示し、グラフの理由、取得データ、SQL、来歴は
右のArtifact／Inspector paneで確認します。actionと対象を画面に表示したうえで、従来どおり費用確認dialogを
通過しなければVertex AIとBigQueryを呼びません。

ダッシュボードbuildが成功すると、俯瞰を優先して右paneを自動で閉じ、共通入力欄を中央下端の小型
「AIに相談」ランチャーへ縮小します。ランチャーをclickするかkeyboardで操作すると、入力下書きとactionを
保持した共通入力欄へ戻ります。復帰後は入力欄内の縮小buttonでもランチャーへ戻せます。pointer接近だけでは
表示を変えません。相談、build、error、ダッシュボード以外の画面では自動縮小しません。

選択中の成果物／分析スレッド名は、左treeの選択行と中央列の44px headerに同じ文言で表示します。中央本文の
上部には同じtitleや説明を大型blockとして繰り返さず、成果物、進行状況、共通入力欄へ縦の領域を使います。
製品版の画面履歴はURLで表現してブラウザの戻る／進むを使う方針です。現在のデモにもワークスペース固有の
重複buttonは置きません。

左ナビゲーションと右の成果物paneは、viewport左右上端の小型ボタンで個別に開閉できます。ボタン座標は
paneの開閉や幅変更で動かず、icon、ラベル、`aria-expanded`が開閉状態に合わせて変わります。
左右paneはviewportの上端から下端までを所有し、中央headerは左右paneの上を横断しません。デスクトップ幅では
それぞれの境界をドラッグして幅を変更でき、キーボードでは境界へフォーカスして左右矢印キーでも
調整できます。右paneは既定330pxのまま、左paneを閉じたdesktopでは中央paneを最低360px残しながら
画面幅の最大75%まで広げられます。取得データの表は上下6pxのcompactな行間で表示します。
pane同士は1px線で隙間なく接し、pointer用の8px操作領域は境界線を中心に重なるため、
見た目の余白にはなりません。横幅が狭い場合は中央の作業領域を優先して右詳細を初期状態で閉じます。変更値は
ローカルデモのページを開いている間だけ有効です。

左側の成果物treeと分析スレッドはデモ用の固定項目または現在の起動中だけを示します。永続履歴、保存、branch、
公開状態、Git連携が実装済みであるようには見せません。左paneは一行title、16pxのicon列、4pxのicon間隔を使い、
長いtitleは折り返しません。省略されたtitleへhoverまたはkeyboard focusすると、同じ行内で横へ流して全文を表示します。

- 左treeの選択titleと中央のcompact headerが一致し、本文上部に同じ大型title／説明blockを置かない
- 共通入力欄が中央列下端に残り、actionごとに既存の費用確認へ接続する
- 共通入力欄が中央列に合わせて縮み、広い画面でも768pxを超えず、通常カードより大きい角丸を保つ
- 共通入力欄が入力内容に合わせて上方向へ伸長し、通常の長文では入力欄内に縦スクロールを表示しない

- 単一グラフの生成物が右Artifact Previewへ移り、取得データとSQLを同じ成果物内で確認できる
- 同じ行にあるダッシュボードカードの境界をdragまたは左右矢印で動かすと、行幅と並び順を変えずに隣接カードが連動する
- パネル選択で行の一部が欠けても残存カードが行幅の100%を使い、折れ線グラフのような単独行は右paneの開閉にかかわらず全幅になる
- 左右paneを両方開く、片方だけ開く、両方閉じる、の各状態で中央が横にはみ出さない

- 760px以下ではカードを一列にし、詳細を開いたときは右paneを画面幅のsheetとして表示する
- 各カードの「詳細を確認」から、理由、SQL、取得データ、来歴へ同じ右paneで移動できる
- keyboard focusが見え、動きを減らすOS設定ではtransitionとanimationを止める

固定応答の数値とグラフはUI検査用であり、最新モデルやBigQueryの品質・費用を再測定した証拠にはしません。
固定fixture上で生成buttonを操作して成功することも、ライブAPIの受入証拠にしません。

ダッシュボードの幅調整は自由配置editorではありません。成果KPI行と診断グラフ行の各境界だけを操作でき、
同じ行の合計幅とカード順は固定します。単独で一行を使うグラフは全幅のままです。dashboard自体の利用可能幅が
900px未満の場合はカードを一列に戻し、resize境界を表示しません。現在のデモでは調整値を保存せず、
再読み込みで推奨比率へ戻します。

#### ダッシュボードを生成する

ダッシュボード生成は、分析目的の相談と仕様確定を、SQL生成・BigQuery実行から分離します。

1. 1つの月次ECサイト分析目的をVertex AIへ渡します。
2. AIが意思決定、最大3件の仮説、読者・比較軸など最大3件の確認事項、KPIとグラフ候補、各パネルが
   支える判断を構造化して提案します。
3. 確認への回答を反映して再提案します。ユーザーは読者・比較の考え方とAIが設計したパネルを編集できます。
4. 確定時に仕様をhash付きrevisionとしてfreezeし、組織コンテキストrevisionとともに生成物へ表示します。
5. 別の費用確認を経て、初めてSQL生成とBigQuery実行へ進みます。

相談中のBigQuery利用料は0円です。AIには対象schema、定義済み指標、利用可能期間、可視化できる結果形状を
渡します。AIは固定候補から選ぶのではなく、目的に必要な分析仕様をtitle、KPI、比較軸、可視化、支える判断、
SQL生成へ渡す日本語の実行仕様として新規に作ります。初回提案数と最大パネル数は管理者設定で、既定は
6件／20件です。過去の6分析は旧デモfixtureの互換経路だけに残し、通常plannerへは渡しません。

AIが指定した可視化特性から2件ずつの行を構成し、Sankeyは単独の全幅行へ配置します。buildが完了すると
作成・編集からダッシュボードへ自動で戻り、右paneを閉じ、共通入力欄を小型ランチャーへ縮小します。
各パネルの「詳細を確認」を押すと、右のパネル詳細で
生成理由、SQL、参照値照合状態、実クエリ結果、パネル来歴をタブ切り替えで確認できます。グラフを
確認する領域へ長いSQLと表を常時展開しません。

SQLはGitHub Light相当の控えめな配色で予約語などを色分けし、改行とスペースインデントを保持します。
KPI・ファネル・時系列・Sankeyは、宣言済みの列数と型に一致する場合だけ描画し、不一致なら停止します。

##### 回遊Sankeyの検査

回遊Sankeyは通常の`page_navigation`として、連続する同一ページビューを1回の滞在へ統合します。
1→2／2→3の段階、同一ページ遷移、edge集約、段階間の接続も検査します。参照値不一致を含む意味上の
不整合があれば、グラフを正常表示しません。

単一グラフで4〜6ページ目までを指定した場合は、指定した最終ページへ到達したセッションから上位12経路を
選び、すべての隣接段階と段階間の流量が揃った場合だけ描画します。短い経路が上位を占めて指定depth未満の
図になることを正常扱いしません。登録済み3ページ設問の参照値と途中終了注記は維持します。

反復、フォームエラー、SPA状態変化は、別の遷移単位を分析計画で選ぶ将来要件です。このデモでは
未実装です。

分析計画、SQL生成、会議報告のVertex AI推定費用は、入力にprompt tokens、出力にcandidate tokensと
thought tokensの合計を使用します。SDK応答にthought tokensが無い場合は0として扱います。この計算は
費用表示だけを補正し、モデル、thinking level、生成回数を変更しません。

##### ダッシュボードbuildの費用確認

2021年1月は登録済み参照SQLでも照合するため、送信前に次の上限目安を確認します。

| 項目 | 上限目安 |
|---|---:|
| Vertex AI | 約¥6（SQL生成6回） |
| BigQuery | 最大240GiB、約¥228 |
| 合計 | 最大約¥234 |

これは、6件の生成SQLと最大6件の参照SQLがすべて20GiB上限まで走り、キャッシュが使えない場合の
上限目安です。

#### 分析候補を相談してから単一グラフを生成する

共通入力欄の「相談」で「どんな分析をしたらいい？」などの探索的な問いを送ると、SQL生成へ進まず、
費用確認後にVertex AIが対象schema、定義済み指標、利用可能期間、利用者の問い、現在の対話履歴から分析案を
新規に設計します。単なる固定候補の並べ替えではありません。「他にない？」のようなfollow-upでは、直前までの
提案を履歴として渡し、同じ案の反復を避けて別の仮説・指標・比較軸を考察させます。

各提案には、分析名、目的、指標、切り口、比較、グラフ種別、理由、SQL生成へ渡す具体的な日本語仕様があります。
提案をpointerまたはkeyboardで選ぶと、その実行仕様を共通入力欄へ反映して操作を「インサイト」に変えます。
相談ではVertex AIだけを1回呼び、BigQuery利用料は0円です。利用者が依頼文を編集してもう一度送信すると
別の費用確認を表示し、承認後だけ
SQL生成・検査・BigQuery実行・描画へ進みます。「インサイト」を選んだまま探索的な問いを送った場合や、
query APIへ同じ問いを直接送った場合も、自動実行せず相談または400応答で停止します。

これは[Evidence Cloud Analytics Agent](https://evidence.dev/product/analytics-agent)の用途別navigation、
quick question、回答からInsightへ進む情報構造を参考にしたデモ範囲です。Evidence Cloudのbrandや固有UIは
複製せず、RepChatの仕様確認と費用gateを維持します。現在はbrowser session内の対話履歴だけを保持する
ローカルプロトタイプです。永続thread、利用者・組織memory、承認済み分析skillへの昇格はIssue #180と
適応型分析メモリー要件の範囲です。

#### 単一グラフを生成する

単一グラフ生成では、1回の送信ごとに次の処理をEvidence基調の同じ画面で進行表示します。

1. Vertex AIによるSQL生成
2. 読み取り専用SQL検査
3. BigQuery実行
4. 結果形状に応じたBigValue・棒グラフ・折れ線・Sankey・表の描画

実行結果は「グラフ」と「取得データ」を切り替えられます。「取得データ」には、描画へ渡した列と行を
そのまま表示します。生成の進行状況には、実行前・処理中・完了・停止・エラーの状態と、SQL生成、
安全検査、データ取得、可視化の現在位置を表示します。

##### 分析対象データを選ぶ

分析対象データは、既存のGA4 ECサイトと、Issue #188の最初の非GA4検証であるBitcoin取引から選べます。

GA4では、問い合わせに書かれた`YYYY年M月`から`_TABLE_SUFFIX`の月初・月末を決めます。公開サンプルの
利用可能範囲は2020年11月〜2021年1月です。範囲外または不正な年月は、Vertex AI・BigQueryの前に
停止します。

登録済みの17設問と完全一致する場合は参照SQLの値とも照合し、それ以外は
「実行済み・既知値未照合」と明示します。未定義指標はSQLを生成せず、不足している定義を表示します。

Bitcoinプロファイルは`bigquery-public-data.crypto_bitcoin.transactions`の`outputs ARRAY<STRUCT>`と、
その内側の`addresses ARRAY`を二段階で`UNNEST`し、取引ごとの異なる受取アドレス数帯を棒グラフにします。
2024年の月を明示した対応設問だけを受け付け、別dataset参照、月パーティション不一致、100行超を
実行前後で拒否します。

基準SQLのBigQuery dry runは約2.91GiB（3,115,504,440 bytes）でした。画面では生成SQLの揺れを
考慮して20GiBをhard limitにし、通常約¥4・最大約¥20を送信前に再確認します。

この経路は、まだ実データ結果・独立レビュー済み参照値を照合していないため「既知値未照合」です。
公開スキーマ1種類の縦切りであり、任意の未知スキーマ対応やIssue #188完了の証拠にはしません。

##### 単一グラフの費用確認

各質問の送信直前に、Gemini 3.6 FlashのVertex AI約¥1、BigQuery最大40GiB・約¥38、合計最大約¥39の目安を再確認します。
無料枠やキャッシュが適用される場合、BigQuery料金は0円になることがあります。

費用確認はページ内のダイアログで行います。「費用を確認して実行」を選んだ場合だけリクエストを
送信し、キャンセルした場合は送信しません。

#### 会議報告案を生成する

確定済みダッシュボードの下にある「この結果から会議報告案を生成」は、追加の費用確認後に、保存済みの
集計bundleだけをVertex AIへ渡します。BigQueryは再実行しません。

48 KiBのbundle、8,192 output tokens、Gemini 3.6 Flashの`LOW` thinkingで制限した上限目安は、
Vertex AI約¥25、BigQuery 0円です。[Google Cloudの価格表](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing)
のtext input $1.50・text output $7.50/100万tokensを用い、回答本文に加えて課金対象の思考tokensも含めます。
出力は観測、解釈、未検証の仮説、推奨アクション、限界を分離し、数値主張へpanel ID、実行SQL hash、
result revisionを付けます。

次のbundle条件では、Vertex AI送信前または表示前に拒否します。

- revisionが一致しない
- bundleが48 KiBを超える

AI応答の一部に根拠の無い数値がある場合は、数値検証を緩めず、その項目だけを除外します。必須区分が
空になる場合は、根拠panelへリンクした数字なしの定型項目で補い、会議報告画面に除外警告を表示します。
limitationsは生成schemaでも数字を禁止します。このフェイルセーフは同じ応答をローカルで検証するだけで、
Vertex AIの自動再実行とBigQuery実行は行いません。

推奨アクションには、期待効果、担当、緊急度、次の一歩、成功指標を表示します。報告案は次の件数までの
会議用要約に制限します。

| 区分 | 最大件数 |
|---|---:|
| 観測 | 3件 |
| 解釈 | 2件 |
| 未検証の仮説 | 2件 |
| 推奨アクション | 2件 |
| 限界 | 3件 |

8,192 tokensまでにJSONが完了しない場合は日本語のエラーで停止し、追加費用を伴う自動再実行は
行いません。

会議報告は常に「未承認案」で、外部共有前の人間確認が必要です。処理中・警告・エラー・完了状態は
会議報告画面に表示し、左ナビゲーションを往復しても保持します。ローカルプロセスは直近1件の確定済み
bundleだけをメモリーに持ち、新しいbuild開始または再起動で破棄します。

承認履歴の永続化、外部配信、目標値・施策履歴の取得、本番認証は未実装です。Issue #181の製品受入条件は
閉じません。

#### グラフ種別と表示契約

任意設問のグラフ種別は結果形状から選択します。`source`・`target`・`sessions`の3列契約はSankeyとして
描画し、同じページ種別は各段階で同色、リンクは遷移元から遷移先へのグラデーションで示します。

複数系列など、それ以外の高度な構成は、事前に分析仕様を確定するショーケースを使用します。

#### ローカルデモの制約

この画面はローカルスパイクであり、本番の認証、gate、executor、顧客Git配送を通りません。

Issue #180の対話とrevision freezeを画面で確認する未検証プロトタイプです。候補パネルは登録済み6件、
組織コンテキストは`demo-org-ec-v1` fixture、buildは同期処理です。本番の任意分析、永続revision、
非同期queue、resume、publication、デザインパートナー評価を満たした製品機能ではありません。

#### 個別確認と回帰測定

1問だけ経路確認する場合は、`QUESTION='<日本語>'`を指定します。任意の日本語はBigQuery実行と
Evidence描画まで行いますが、登録済みの参照値とは照合せず「実行済み・参照値未照合」と表示します。

17問の回帰測定を再実行するときは、`SHOWCASE`と`QUESTION`を省略します。R1〜R15の過去基準は
2回連続15/15です。R16の移動平均とR17の回遊はIssue #178で追加したため、17問全体の再測定は
別途記録します。

## 画面に出る2種類のSQL

| 表示 | 実行場所 | 役割 |
|---|---|---|
| BigQueryへ送ったSQL（AI生成・検査済み） | BigQuery | 公開データを集計する。`SELECT *`を実行前に拒否し、必要列だけを明示する。BitcoinプロファイルではGoogleSQL予約語の裸の`hash`だけを`` `hash` ``へ意味を変えずに補正し、その実行SQLを表示する。それ以外は表示時だけ整形し、実行SQLを変更しない |
| Evidenceでの描画用SQL | materialize後のDuckDB層 | BigQuery結果から描画に使う列を明示して読む。BigQueryへは送らない |

この区別を画面内に出すのは、Evidence側の`select ... from ga4.q1`だけを見て、手書きSQLを
描画していると誤認させないためです。どちらのSQLにも`SELECT *`は出力しません。生成SQLは
SELECT列ごとの4スペースインデント、主要句の改行、大文字キーワードを適用したEvidence標準の
コード領域に表示し、長い式は横スクロール・コピーできます。ショーケースでは各分析の
「分析結果」「生成プロセス・SQL」「集計データ」を同じタブセットに置き、グラフ、SQL、実クエリ結果の
対応を記憶させません。

この同居は機能確認デモ専用です。製品版は閲覧者向けのグラフ／表と、権限を持つ分析担当者向けの
SQL・定義・来歴を分離し、選択したグラフから文脈を保って移動する設計をIssue #179で検討します。
この対話・仕様確定・buildはIssue #180のローカル未検証プロトタイプです。根拠付きの会議向け所見はIssue #181です。
