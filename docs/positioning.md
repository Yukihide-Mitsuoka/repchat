# ポジショニング

## この文書の役割

[competitive-landscape.md](competitive-landscape.md) が「既存製品は何を持っているか」の**事実**なら、
これはそこから導いた**方針**です。**何で戦い、何で戦わないかを先に決めておく**ためのもので、
実装の優先順位はここから逆算します。

**確定していないものは「仮説」と明記しています。** 確定と仮説を混ぜると、未検証の前提の上に
実装が積み上がります。このプロジェクトは一度それをやっています。

## 0. 前提の確認 — 勝負の土俵

**市場を取ることは目標ではありません。** 目標は顧客3〜5社で副業として黒字（LOG-0021）。

この2つは必要条件がまったく違います。

| | 市場を取る | 3〜5社で黒字 |
|---|---|---|
| Holistics / Omni に機能で勝つ必要 | ある | **無い** |
| 必要な売上 | 数億円規模 | **月30万円**（1社20人×5,000円×3社） |
| 必要な差別化 | 恒久的な堀 | **その3社が選ぶ理由** |

**「Holistics に勝てるか」と「日本の小さな会社3社が月10万円払うか」を混同しない。**
比較表が厳しく見えるのは前者の問いで読んだときです。

## 1. 続ける根拠 — 現金が燃えていない

インフラは Cloud Run（ゼロスケール）＋ Cloudflare Workers（$5/月）＋ Neon（無料枠）で、
**顧客ゼロでの維持費はほぼゼロ**です。

「顧客がいないなら作るな」という原則は、**現金が燃えている場合の話**です。燃えていないなら、
失うのは時間だけで、続ける判断は合理的です。

**ただし時間は有限**なので、後述の「効かないもの」に時間を使わないことが条件になります。

## 1.5 観測された痛み（2026-07-27 追記）

**この節だけが仮説ではありません。** GA4 と Amplitude の代理店で実際に起きていることです。
以下の方針はここから逆算しています。

**Looker Studio 側** — 代理店がレポート制作に使っていた共有アカウントが廃止されることになり、
移行に相応のコストが発生している。顧客側でも**データ接続をした人やレポート作成者の退職**で
資産が失われ、アクセス制御の問題を抱えている。**Looker Studio Pro（$9/人・月）に入っても、
閲覧範囲と権限の管理は設計を要する。**

**Amplitude 側** — **解約の主因が「使いこなせない割に高い」**。Amplitude は分析レポートを
簡単に作れる製品なので、**「作るのが難しい」という説明が消えます**。残るのは
**「何を分析すべきか分からない」**。

**この2つは別々の仮説を裏付けています。**

| 観測 | 裏付けられるもの |
|---|---|
| Looker Studio の退職・権限問題 | **この構想の元々の動機**（所有権・ガバナンス） |
| Amplitude の解約理由 | **「何を見ればいいか分からない」仮説**（2.1の前提） |

**強制イベントが効いています。** 共有アカウントの廃止は**期限のある移行**です。人が乗り換えるのは
不満があるときではなく、**どのみち何かを変えなければならないとき**です。ただし**移行を終えれば
扉は閉じます**。

**価格の基準が $9 に引かれてしまっている**ことも、ここから来ます（[competitive-landscape.md](competitive-landscape.md)）。

## 1.6 OEM 経路 — 流通を解く

**単独の最大の障害は機能ではなく流通**（実績のない個人がどう最初の顧客に届くか）です。
OEM はそこを迂回します。

**設計はそのまま使えます。** `vendors` → `tenants` → `users` の3階層と `vendor_keys` は、
もともと「ベンダーが自社顧客に埋め込む」ために作ったものです。直販方針で休眠させようとした層が、
**OEM では主役に戻ります**。[.ai/mission.md](../.ai/mission.md) の元の記述は、
**書き換えるべきものではなく両立させるべきもの**だった可能性があります。

**代理店は流通だけでなく、中身も持ってきます。** 2.1 で必要とした「何を見るべきか」の知識を
持っているのは代理店です。**その知見がテンプレートの中身になれば、業種知識を自前で獲得する
必要がありません。** 横断的なグローバル製品には真似できない部分です。

**必ず来る反論**: 「Looker Studio でいいのでは」。無料の製品が既にあるので、
**直販でも OEM でも最初に来ます**。答えは所有権・退職耐性・権限管理・コード管理・AIですが、
**口頭ではなく見せられる形にしないと通りません**。

**注意すべき点**: 相手が売るのをやめれば顧客はゼロに戻る（1社依存）。OEM は相手が取り分を持つ
（利幅）。ソリューション提案しかしてこなかった組織に製品を売らせるには**説明資料・デモ・想定問答**が
要る（2.2の投資と同じもの）。

**相手は1社に限りません。** 「一つ長けていて顧客は抱えているが売る製品がない」という構造は、
Web制作会社・POS/ERPベンダー・会計事務所など**広く当てはまります**。利益相反の無い相手を選べます。

## 2. 採る — 戦えるポイント

優先順位つき。上ほど、単独の個人事業主が構造的に有利です。

### 2.1 業種を絞る（最優先・ただし仮説）

比較表で唯一空いている「**何を見ればいいか分からない人**」を埋めるには、AIが**正しい**
ダッシュボードを作れる必要があります。スキーマだけからは作れません。売上と粗利のどちらを見るか、
季節性をどう扱うかは**業種の知識**です。

横断的な製品はこれをやりません。**全業種に効くテンプレートは存在しない**からです。裏を返せば、
**1業種に絞れば、世界的な横断製品が構造的に降りてこられない場所**になります。

> 飲食チェーンなら店舗別・時間帯別・曜日別・原価率。ECならリピート率・LTV・カゴ落ち。
> **「接続したら、その業種で見るべき10枚が最初から入っている」**は汎用製品にはできません。

**単独であることを初めて有利に使える角度**です。**業種は未定** — ヒアリングで最初に反応した
業種に寄せるのが自然です。

**ただし、必須条件ではなくなりました。** 2.7 の入口設計（既存の手作業レポートを入力にする）を
採ると、**顧客自身がドメイン知識を持ち込みます**。業種テンプレートは
**必須条件ではなく加速装置**になり、**無い状態でも成立します**。単独で始めるにはこの差は大きい。

### 2.2 日本語ドキュメント

海外製品は英語で、かつ dbt やウェアハウスの知識を前提にしています。
**「日本語で、自社のBigQueryに繋ぐ手順が最初から最後まで書いてある」**は、
エンジニア1人の会社には実質的な差です。

**追加コストがほぼゼロの差別化は稀**なので、優先度は高い。

### 2.3 AIへのデータ受け渡しの説明責任

日本企業の情報システム部門が聞くのは「**業務データはどのAIに渡り、どこで処理されるのか**」です。
海外製品は英語のDPAで答えますが、それでは稟議が通りにくい。

[ai-governance-requirements.md](ai-governance-requirements.md) の**列単位の宣言的マスキング**が、
そのままこの問いへの答えになります。加えてモデル選択・BYOK・処理リージョンの明示。

**「薄く付ける」のではなく、争点を選んで答える**こと。

### 2.4 請求書払い・銀行振込

Evidence Cloud も Metabase も**クレジットカードの自己申込**です。日本のSMBには、
業務ソフトをカード決済する稟議が通らない会社が実在します。

**個人事業主なら明日から対応でき、海外SaaSには当面できません。** 地味ですが決定的な場面があります。

### 2.5 接続作業をサービスに含める

「エンジニア1人が30分」を**弱点ではなく提供物**にします。「最初の接続は一緒にやります」。
海外のセルフサーブ製品には原理的にできません。

なお接続がサービスアカウント方式であること（[ADR-0010](adr/0010-connection-identity-is-never-a-person.md) D1）は
ここでも効きます。**担当者が辞めても接続が壊れない**ので、一度やれば終わりです。

### 2.6 価格（単独では堀にならない）

Gemini Flash が1問約¥0.1、インフラも数千円規模なので、**Evidence Cloud の $15/人・月を下回っても
十分黒字**です。

ただし**価格は真似されます**。下げるなら 2.1〜2.5 のいずれかとセットにすること。
**価格だけを理由に選ばれた顧客は、価格だけを理由に離れます。**

### 2.7 入口は「既存の手作業レポート」にする

**「何を見たいですか」と聞いてはいけません。** 何を見ればいいか分からない人は、
**何が欲しいかも言えません**。

しかしその人は、**毎月Excelで手作業のレポートを作っています**。上司に出す資料、会議で配る数字。
**形式は既に存在します。** 「いつも作っている資料を見せてください」なら答えられます。
**発明せず、今やっていることを渡すだけ**です。

そのレポートには**その会社にとって何が重要かが埋め込まれています** — どの指標を、どの粒度で、
どう並べるか。**顧客自身がドメイン知識を持ち込む**ことになります（2.1 の前提が緩む理由）。

**最小の流れ**:

> 手作業のレポートを渡す → DWH に接続 → **スキーマとの対応づけをAIが提案し、不明点だけ質問** →
> SQL と Evidence ページを生成 → **既知の数値1つで照合** → 人が承認してコミット

**設計上の要点3つ。**

**接続してから提案する。** スキーマを見ずに「売上」と言われても列は決まりません。
**対応が付かない欄は推測せずに聞く**こと。Holistics が「曖昧なら聞き返す」を売りにしているのは、
ここが事故の元だからです。

**出力はレビュー可能な成果物にする。** チャットは流れて消えますが、エクスポートされるのは
**Evidence の markdown と SQL**。「相談 → ダッシュボード」ではなく
**「相談 → レビュー可能な差分 → ダッシュボード」**です。

**正しさの検証を最初から入れる。** **見た目が正しくて数字が間違っているレポートは、無いより悪い。**
顧客に**既知の正解を1つ**聞く（「先月の売上は◯◯円のはず」）。生成SQLがそれを再現できれば
対応づけが合っている強い証拠になります。**手作業レポートを入力にすると、
入力と検証データが同時に手に入ります。**

**機構では差別化しないこと。** 「AIと相談して分析を組み立てる」は Omni の agent 等が既に持ち、
今後コモディティ化します。守れるのは機構ではなく、**既存レポートを起点にする体験**
（Omni はデータモデル作成から始まる）、**日本語**、**成果物が顧客に残る所有権**、
**代理店の知見がテンプレートに乗ること**です。

### 2.8 セマンティック層は選択肢ではなく必須

Amplitude の上流の作り込み（イベント設計・タキソノミー）は重いが、
**ファネル・リテンション・コホートという語に意味を与えていました**。

DWH に直接SQLを投げれば作り込みを飛ばせますが、**意味も一緒に飛びます**。

> **理由を訂正しました（2026-07-27、[spikes/report-generation](../spikes/report-generation/README.md)、LOG-0065）。**
> 当初ここには「生イベントからのセッション化・`UNNEST` の重ね合わせは自然言語SQLが最も苦手な領域」と
> 書いていました。**実測で外れました。** GA4の生エクスポートに対し、セッション定義も `UNNEST` も
> ファネルも**正しく書けています**。
>
> **本当の理由は、難しさではなく不安定さです。** 落ちたのは「購入件数」と「新規訪問」——
> どちらも**モデルの解釈も参照実装も、それぞれGA4として妥当**で、数字だけが違いました。
> さらに `temperature=0` でも**実行のたびに解釈が変わりました**（購入件数が回によって
> `COUNT(*)` と `COUNT(DISTINCT transaction_id)` の間で揺れる）。
> **同じ問いで月ごとに数字が変わるレポートは、月次レポートとして失格です。**
>
> **追試で裏付けました（LOG-0066）。** 最小の定義層（購入件数と新規判定を含む）を渡して3回走らせると、
> **数値は12/12で完全一致**し、揺れていた購入件数も 895 に固定されました。
> **一方でSQLの文面は12中7で毎回変わっています** —— つまり**定義が固定するのは意味であって構文ではなく、
> 必要なのは前者**です。生成SQLをキャッシュして固定する必要はありません。
>
> ただし**定義層の守備範囲が1つ足りません**。ファネルは数値が完全一致したまま
> 縦持ち／横持ちが参照と食い違いました。**指標の意味だけでなく、出力の形も宣言する必要があります。**

したがって**「接続してSQLで聞けば作り込み不要」は、定義が自明な集計については正しく、
定義に幅がある指標については正しくありません。** 「セッションとは何か」「購入件数とは何か」を
**一度決めて固定する**必要があります — Amplitude の作り込みの軽量版です。
**そしてその定義を書けるのも代理店**なので、顧客ごとにやり直す必要はありません。

**位置づけの結論**: 「Amplitude を安くSQLで置き換える」ではありません。それでは難しい分析が
できなくなった分だけ悪くなります。**「代理店が正しいと知っている分析が定義済みで入っていて、
日本語で聞けて、資産が顧客に残る」**が売り物です。

### 2.9 未決 — 生成物の Git をどちらが持つか

「本体はこちらでホスト、**生成したページとSQLは顧客側の Git**」という案は、
**資産が残るという主張を本物にします**。解約しても手元に残るなら、
**払い続ける理由とやめても損しない安心が同時に立ちます**。逆説的ですが**やめやすい方が入りやすい**。

**ただし前提が増えます** — 顧客側に Git リポジトリと PR を理解する人が要り、
**「非エンジニアでも使える」と正面から衝突します**。

**ADR を1本立てる論点**です。ここで即決せず、独立した設計判断として扱ってください。

## 3. 採らない — 時間を使わないもの

**明示しておかないと、機能表の空欄を埋めたくなります。**

| 採らないもの | 理由 |
|---|---|
| **BI機能そのもので追いつく** | 到達しても差にならない。相手は資金を得た企業で先に持っている |
| **英語圏での勝負** | 言語・サポート・商習慣という唯一の優位を捨てることになる |
| **価格だけの勝負** | 真似される。2.6参照 |
| **Metabase型のGUI探索UI** | 莫大な工数で、勝てない。**自然言語がGUIの代わり**という設計方針（LOG-0061の議論） |
| **セキュリティ機能の網羅** | 行レベル権限は全社が持っている。優位は「接続が退職で壊れない」設計思想であって機能数ではない |

## 4. 事業の性質が変わることの直視

その3社が選ぶ理由は、**機能ではなくなります**。日本語であること、請求書で払えること、
困ったら日本語で人に聞けること、最初の接続を一緒にやること。

**それはソフトウェア事業というより、サービス業に近い形**です。利益率も再現性もソフトウェアより低く、
**founder 自身が製品の一部**になります。

**副業として成立するかは、ここにかかります。** 顧客3社が毎週質問してくる状態なら持ちません。
2.2 の日本語ドキュメントは差別化であると同時に、**サポート工数を下げる投資**でもあります。
そう位置づけると優先度が上がります。

## 5. 未検証の仮説と、検証方法

**この文書の方針は、以下が崩れると変わります。**

| 仮説 | 検証方法 | 崩れたらどうなるか |
|---|---|---|
| ~~「何を見ればいいか分からない」が実在する痛み~~ | **1.5 で裏付け済み** — Amplitude の解約理由。作りやすい製品でも使いこなせない＝「作るのが難しい」が主因でないことの実観測 | — |
| ~~所有権・権限管理が実在する痛み~~ | **1.5 で裏付け済み** — Looker Studio の共有アカウント廃止と、接続者・作成者の退職 | — |
| **今レポートを作っている人が、明日も作れるか** | **最大の関門。** Looker Studio はドラッグ&ドロップで非エンジニアが作れる。こちらは「自然言語→PR→承認」で**同じ人が同じようには作れない**。今 Looker Studio でレポートを作っている人に、2.7の流れで1枚作ってもらう | **他が全部揃っても売れません。** 唯一かつ最大の判定条件 |
| 生成された数値が正しい | 2.7 の**既知の数値照合**を組み込み、実データで確認 | 見た目が正しく数字が違うレポートは無いより悪い |
| 日本語のNL→SQLで海外製品に差をつけられる | **日本語スキーマ・日本語質問20問のベンチマーク**を作り、自社／Evidence Cloud／Metabase の試用で同じ問題を流して正答率を比較 | 2.1・2.2の価値が下がる。逆に差が出れば測定された差別化になる |
| 日本のSMBが海外SaaSを使わない理由が言語・支払い・サポートにある | 同じヒアリングで「Evidence Cloud を知っていますか／なぜ使わないのですか」 | 2.2・2.4が崩れる |

**判定条件は先に決めておくこと。** 決めずに聞くと都合よく解釈します。

**やめる条件**: 多くが「使いこなせている」「必要ない」「Evidence Cloud で足りる」と答えること。
**やめるのも正しい結論**です。

**次にやるべきことは設計ではなくデモです。** 1.5 で痛みは観測済みなので、残る関門は
「**今作っている人が明日も作れるか**」ひとつ。**実データに繋いで、自然言語でレポートを1枚作り、
権限を設定し、それが Git に残っている**状態を作って、**今 Looker Studio でレポートを作っている人に
触ってもらう**。売り込みではなく「これで作れますか」と聞くだけです。

**測るのはSQLの正しさではなく、非エンジニアが自然言語でレポートを作れるかどうか**です。

## 6. mission.md との不一致（未解消）

[.ai/mission.md](../.ai/mission.md) は依然として**「顧客に埋め込みたいベンダー」を主要ユーザー**と
記述しています。この文書は**直販・ユーザー単位課金**を前提にしており、**矛盾しています**。

方針が確定したら mission.md を先に更新し、この節を消してください。
確定に必要なのは3点 —
**対象企業の定義**（「DWHにデータがあり、技術者が1人いて、データ専任者はいない会社」で良いか）、
**閲覧者と作成者の課金区分**、**認証方式**（SSO推奨）。
