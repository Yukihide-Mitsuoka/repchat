# AIガバナンス要件

## この文書の役割

**今すぐ作るもののリストではありません。** 「どの機能が、どの価格帯を売るための前提条件になるか」と、
**それぞれの着手条件（トリガー）**を記録したものです。

同じ判断を将来の自分（または別のエージェント）が再現できるように、**結論だけでなく理由と、
採らなかった選択肢とその理由**を残します。機能リストだけを残すと、数ヶ月後に「セキュリティ機能が
足りない」という理由で、顧客のいないまま作り始める誘因になります。それは避けたい失敗です。

**読むべきとき**: AI分析レポート機能に着手するとき、列レベル制御を設計するとき、
顧客の情報システム部門からデータ取り扱いを問われたとき。

## 前提（未確定であることの明示）

この分析は 2026-07-27 の議論で出た製品方針に依拠しています:

- 売り先は**埋め込みたいベンダーではなく、直接の顧客企業**
- 課金は**ユーザー単位**（基本料＋作成者席＋閲覧者席）
- **AI分析レポート機能**を上位層（月10,000〜15,000円/人）として想定

**この方針は [.ai/mission.md](../.ai/mission.md) にまだ反映されていません。** mission.md は依然として
「ベンダー向け埋め込み分析」を主要ユーザーと記述しています。方針が確定したら mission.md を先に
更新し、この文書の前提節を消してください。**前提が変われば、以下の優先順位も変わります。**

## 中核の判断 — 前提条件は連鎖する

この製品では、**売り物そのものではないが、それが無いと売り物を売れない層**が繰り返し現れます。

| 売りたいもの | その前提条件 | 前提条件が無いとどうなるか |
|---|---|---|
| ダッシュボード（基本層） | **テナント分離・接続主体の非属人化** | 顧客が自社DWHへの接続を許可しない |
| **AI分析レポート**（上位層） | **列レベルのデータ取り扱い制御（マスキング）** | 顧客が業務データのLLM送信を許可しない |

**同じ構造が一段ずつ上で繰り返されている**、というのがこの文書の中心的な認識です。

そして重要な接続がひとつあります。**「マスキング」と、[status.md](status.md) に未実装として
残っている「列レベル制御」は、同じものです。** 別々の課題として管理すると、片方だけ作って
もう片方を作り直すことになります。

### なぜ分析機能でだけマスキングが要るのか

LLMに何が渡るかが、機能によって決定的に違うためです。

| 機能 | LLMに渡るもの | マスキングの必要性 |
|---|---|---|
| NL→SQL（レポート生成） | **スキーマのみ**（テーブル名・列名） | 低い |
| AI分析レポート | **実データ**（数値・顧客名・担当者名） | **必須** |

現在の構想では NL→SQL はスキーマしか見ません。しかし「レポートを読んでAIが所見を書く」機能は、
**定義上、業務データをLLMに送ります**。上位価格の根拠となる機能が、そのまま最大の
データ取り扱いリスクでもある、という関係です。

### RepChat の構造的な優位

汎用のAIガバナンス製品は、Gmail や Slack の**非構造テキストからPIIを検出**しなければならず、
検出漏れが原理的に避けられません。

RepChat は**列単位でデータの意味が分かっています**。したがって検出ではなく**宣言**にできます
——「この列は個人情報なので分析には渡さない」。宣言は漏れません。**セマンティック層を持つことの
副次的な利点**であり、後追いの検出では到達できない品質です。

## 参考にしたもの — AI MONBAN（DataSign）

2026-07-27、オーナーが提供したウェビナー資料より。**AIとエンタープライズデータ（Gmail / Notion /
Slack / Salesforce / GitHub）の間に立つMCPゲートウェイ**。RepChat とは**カテゴリが違います** ——
向こうは既存AIツールを統制する層、こちらは自分自身がAIツールです。したがって**そのまま移植すると
的外れになります**。

以下は6機能それぞれについての、RepChat における扱いと理由です。

| 向こうの機能 | RepChat での扱い | 理由 |
|---|---|---|
| **マスキング** | **採る（最優先）** | 上位層の前提条件。列レベル制御と同一物 |
| **AI管理**（モデル選択・BYOK） | **採る（部分的）** | 購買部門の質問への回答。「野良AI排除」の側面は不要 |
| **接続管理** | **採る（UIのみ）** | 状態が見える画面は要る。**OAuth方式は採らない**（後述） |
| **アクセス制御** | **既にある** | ロール→レポート→行スコープとして実装済み |
| **操作ログ** | **部分的に既にある** | レポート定義はGitが担う。**権限変更の履歴は穴**（後述） |
| **データアクセスログ** | **現状維持** | 応答本文の記録は**意図的に採らない**（後述） |

## 採らない判断と、その理由

将来「なぜこれが無いのか」と問われたときのために、**採らなかった理由**を残します。

### OAuth による接続（採らない）

参考資料の接続管理画面には `OAuth token expired. Re-authenticate to restore access` という
エラーが表示されていました。**これは、この製品が解こうとしている問題そのものです。**

OAuth接続は個人アカウントに紐づくため、期限切れや**担当者の退職で壊れます**。Looker Studio で
レポートとデータソースが消える問題と同じ根です。RepChat がサービスアカウント方式
（[ADR-0010](adr/0010-connection-identity-is-never-a-person.md) D1「接続主体は決して人ではない」）
を採っているのは、**この失敗モードを構造的に起こさないため**です。

非エンジニアでも設定できるという理由でOAuthを採用したくなったら、この節を読み返してください。
**設定の容易さと引き換えに、製品の中心的な売り文句を失います。**

### 応答本文（クエリ結果）のログ記録（採らない）

参考資料は、リクエストとレスポンスの本文をマスク済みビューで記録していました。「誰が何を**見たか**」
まで分かります。

RepChat では**「何を問い合わせたか」までに留めます**。理由は、結果データを保存すればそれ自体が
情報資産となり、保持期間・暗号化・漏洩時の影響範囲が新たな管理対象になるためです。
**顧客から「そちらにデータは残るのか」と問われる材料を、自分から増やすことになります。**

必要になったときに、**顧客が選べる形で**追加します（既定は無効）。

### AI管理のうち「野良AI排除」（不要）

向こうの中核機能ですが、**RepChat にはAIが1つしかありません**。必要なのは「どのモデルを使うか」
「顧客のAPIキーを使えるか」の選択だけで、これは別物です。

## 既知の穴 — 権限変更の履歴

レポート定義の変更履歴は **Git がそのまま担います**。これは Evidence を土台にしたことの利点で、
作る必要がありません。

しかし**権限設定（ロール、行スコープ、レポート割り当て）は Postgres にあり、Git には残りません**。
「誰がいつ、誰に何の権限を与えたか」の履歴が現状ありません。**内部統制監査では必ず問われる部分**です。

安易に「権限もGitに置けば履歴は無料」と考えないでください。
[ADR-0010](adr/0010-connection-identity-is-never-a-person.md) D7 が
**「細かく実行時に変わる境界はデータ層に委ねない」**と述べており、権限の即時剥奪と
Gitのレビューサイクルは相性が悪い。現時点での見立ては
**「レポート定義はGit、権限はDB＋変更履歴テーブル」**です。

## 着手条件（トリガー）

**いずれも「無いと動かない」ものではなく「売るために要る」ものです。**
顧客がいない段階で作り始めるのは、この製品が一度通った失敗の反復になります。

| 項目 | 着手条件 |
|---|---|
| 列レベル制御＋マスキング | **AI分析レポート機能に着手すると決めたとき**。分析機能より先に設計する |
| モデル選択・BYOK | 顧客の情報システム部門から**LLMの取り扱いを問われたとき**。聞かれる前に作らない |
| 接続管理UI | **2社目の接続作業をするとき**。1社なら手作業で足りる |
| 権限変更の履歴 | **顧客に監査要件があると分かったとき**、または権限変更が事故を起こしたとき |
| 応答本文ログ | 顧客が**明示的に要求したとき**のみ。既定では作らない |
