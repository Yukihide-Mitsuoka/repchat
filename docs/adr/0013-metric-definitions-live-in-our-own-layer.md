## Context（強制する問題）

自然言語からレポートを生成する経路を実測したところ、**壊れるのはSQLの生成ではなく、指標の定義**
だと分かった（LOG-0065）。GA4の生エクスポートに対し、セッション化・`UNNEST`・ファネルまで
**正しく書けた**一方、「購入件数」は `COUNT(*)` と `COUNT(DISTINCT transaction_id)` の間で、
「新規訪問」は `first_visit` と `ga_session_number = 1` の間で**実行ごとに解釈が変わった**。
`temperature=0` でも揺れる。**同じ問いで月ごとに数字が変わるレポートは、月次レポートとして失格。**

最小の定義層を渡す追試で、**数値は3回とも12/12で完全一致**した（LOG-0066）。同時に、
**SQLの文面は12中7で毎回変わっていた**。つまり**定義が固定するのは意味であって構文ではない**。

自作の前に既存OSS（WrenAI、Apache 2.0）を実機評価した（LOG-0067/0068）。MDLはGit前提のYAMLで、
LLMを持たず意味層のみを提供する良い設計だが、**GA4を表現できない** —— `ref_sql` は `UNNEST` を
通すがワイルドカードを書けず、`table_reference`＋計算列はワイルドカードを書けるが `UNNEST` を
書けない（式中の識別子をモデルの宣言列に対して解決するため `key` が見つからない）。
**平坦化をMDLの外＝BigQueryのビューに置く必要がある。**

### 強制する力

- **オーナーの評価基準**（LOG-0028以降、明示）: 実装工数は度外視し、**堅牢性とセキュリティで加点、
  コストと速度の犠牲で減点**。そして**保守工数は堅牢性に含まれる**（recurring だから）。
- **ADR-0010 D1**: 接続主体はテナント別の機械IDで、**鍵を持たない**。実測で裏付け済み
  （LOG-0052、LOG-0059）。このプロジェクトで**最も検証された性質**。
- **ADR-0010 D3**: セキュリティ実装が**コネクタ数に比例してはならない**。
- **ADR-0010 D6**: 制御の採否は、**保守が滞ったときにどちらへ倒れるか**で決める。
- **ADR-0010 D7**: **粗く滅多に変わらない境界**はデータ層に委ねてよい。細かく実行時に変わるものは委ねない。
- **WrenAIのBigQueryコネクタは `credentials`（SA鍵）を必須**とし、ADCを受け付けない（LOG-0068）。

## Decision

### C1. 指標定義は自前の層に持つ。WrenAI/MDL は採用しない（形式のみ参考）

定義層は**こちら側の1箇所**に置く。`spikes/report-generation/metrics.json` を育てた形が原型。

MDLの**構造は参考にする** —— `knowledge/` の rules / metrics / glossary / caveats という切り分けは
良い整理で、そのまま設計語彙として使える。しかし**エンジンを依存に入れない**。
GA4を表現できない以上、入れても平坦化の問題が残り、**依存だけが増える**。

Apache 2.0 なので採用自体に法的障害はない（改変部分を非公開のままSaaS提供可、義務は帰属表示と
改変明記§4b、**商標は非許諾§6**）。**採らない理由は法務ではなく、解けない問題が残ることと保守。**

### C2. 平坦化は自前の生成層で行う。BigQueryビューは既定では使わない

顧客環境にビューを作らせる案（および、こちらが書き込み権限を得て作る案）を**却下する**。
理由は3つで、いずれも堅牢性の減点。

**保守工数が顧客数に比例する。** 指標を1つ足して列を追加したくなるたび、**全顧客にDDLの再実行を
依頼する**ことになる。これは **D3が禁じた形の再発**で、比例するのがコネクタ数かビュー数かの違い
しかない。オーナーの基準では、recurring な保守は堅牢性の減点。

**壊れているのに直せない状態を作る。** ビューは顧客のプロジェクトにある。GA4の仕様変更、誰かの削除、
権限変更 —— **こちらから修復できない**。連絡して待つしかない。

**書き込み権限案は、最も検証された性質を捨てる。** D1の読み取り専用性を失い、しかも
**権限は放置されると広いまま残る＝開く側に倒れる**（D6違反）。

ビューは**アーキテクチャではなく個別最適化**に降格する。特定顧客で必要と**測定できたとき**にのみ、
その顧客に限って検討する。

### C3. 定義が固定するのは「意味」であって「構文」ではない

**生成SQLをキャッシュして固定しない。** 実測では、文面が毎回変わっても数値は完全に一致した
（LOG-0066）。固定すべきは定義であり、SQLの別名・整形・CTE構造は揺れてよい。

これは実装要件を1つ**消す**: SQL生成の決定性は要件ではない。**定義の一意性が要件**。

### C4. 定義は「指標の意味」と「出力の形」の両方を宣言する

LOG-0066 の残った1件（ファネル）は、**数値が完全一致したまま縦持ち／横持ちが食い違った**。
どちらもレポートとして正しく、**決めておかないと決まらない**。

指標の式だけでなく、そのセクションが**何行何列で出るか**も宣言対象とする。

#### 実測（2026-07-28、LOG-0072）— 宣言は効くが、宣言の中身を取り違えると壊れる

**形状を宣言するとファネルの揺れは止まった**（4回の実行すべてで安定）。C4 の主張は成立する。

**ただし、宣言しただけでは他の3セクションが壊れた。** 宣言した列名を、モデルが**SQLの識別子として
そのまま使った**ため —— `AS 日付` は構文エラー（BigQuery は非ASCII識別子を裸で受け付けない）、
`リピートユーザー率（％）` はバッククォートで囲んでも**フィールド名として不正**（全角括弧は使えない）。

**したがって C4 の宣言は「表示名と順序」であって「SQL識別子」ではない。** 両者を分離し、
**SQLの別名は ASCII の snake_case、表示名はレポートを組み立てる側が付ける**としたところ、
**2回連続で 15/15**（未定義3件の拒否を含む）。

この分離は Evidence の使い方とも一致する —— コンポーネントは `title` を data とは別に受け取るので、
**表示名はSQLに埋め込む必要がない**。

### C5. 定義にある語は再解釈させない。無い語は生成せず、問い返す

定義済みの語は、モデルに自分で解釈し直させない。**定義に無い指標を求められたら、推測でSQLを
生成せず、定義の追加を促す**（fail closed）。

推測を許すと、C3で得た再現性がその1問だけ失われる。**どの数字が定義済みでどれが推測か、
レポートの読み手には区別がつかない。**

#### 実測による補正（2026-07-28、LOG-0070）

起草時、C5 は**このADRで唯一の未実測の決定**だった。測ったところ、
**意図は成立したが、境界の引き方が誤っていた**。

**成立した側**: 真に未定義な3語（直帰率・平均滞在時間・離脱率）は**3/3で拒否**。
とくに「平均滞在時間」は、定義済みの「エンゲージメント時間」が近くにあるにもかかわらず
**代用しなかった** —— C5が最も効いてほしい場面。

**誤っていた側**: **言い換えを未定義と判定して過剰拒否した。** 設問の「新規訪問」に対し、
定義は「新規セッション」。モデルは
「定義済みの『新規セッション』で代用せず、未定義語として処理します」と明示的に拒否した。
説明的な言い回し（「商品を見たセッション数」）も同様。しかも**実行ごとに揺れる**
（同じ設問が回によって通ったり拒否されたりする）。

**したがって C5 の判定基準は「語が字面で一致するか」ではなく「意味が定義に解決できるか」である。**
これを満たすには、定義に**別名・言い換えを持たせる**必要がある
（WrenAI の `knowledge/glossary/` が別立てになっているのは、おそらくこの理由。C1で形式を参考にすると
述べた部分に、glossary が含まれる）。

#### 補正の検証（同日、LOG-0071）

別名を定義に持たせ、あわせて**合成の規則**（**定義済みの指標を宣言済みの列で絞り込む・分割するのは
「代用」ではない**）を追加して再測した。過剰拒否は**2種類**あり、別名だけでは片方しか解けなかったため。

**境界は正しくなった。** 2回の実行で、真に未定義な3語は**両方とも拒否**、言い換えと合成は
**両方とも回答**。**過剰受容も起きなかった** —— `滞在時間` を「エンゲージメント時間」の別名に入れて
「平均滞在時間」と衝突させたが、両実行とも拒否している。

**残った不安定は出力形状だけ。** 2回の差はファネルの縦持ち／横持ちのみで、数値は一致していた。
**C4 が未実装であることの現れ**であり、C5 の問題ではない。

**D3 の確認**: 別名は45個／12定義。ただし**これは GA4 の語彙**であり、GA4を使う顧客なら
**同じものを使い回せる**。標準化されたデータソースでは**顧客数に比例しない**。
顧客固有の業務データについては未測定で、そこは別途確認が要る。

### C6. 生成結果は、使う前に既知の数値と照合する

`spikes/report-generation` の gold 照合を、製品の経路にも置く。本番では**顧客が持っている
先月の完成品**がその役割を果たす（既存の手作業レポートを入力にする設計＝positioning §2.7 の副産物で、
**入力と検証データが同時に手に入る**）。

照合できないセクションは、**数値を出さずに未検証と表示する**。
見た目が正しくて数字が違うレポートは、無いより悪い。

### C7. 定義の置き場所はADR-0014で決定済み

本ADRの起草時には、positioning §2.9 の論点として独立したADRへ先送りした。
[ADR-0014](0014-who-owns-the-generated-artifacts.md) がその論点を引き取り、accepted になった。

決定は、**ページとソース定義を顧客のリポジトリ、指標定義をこちら側**に置く3分割。
顧客はGitを操作せず、こちらが書き込む。顧客固有の指標だけは例外として顧客側に置ける。
C1〜C6 の内容はこの配置決定によって変わらない。

## Consequences

**得るもの。** D1が無傷で残る（読み取り専用、鍵なし）。保守が顧客数に比例しない。
壊れたときに自分で直せる（今日、`QUERY_POLICY` の取り違えも `tokenCreator` の断絶も、
自分で直せたから数十分で解決した）。依存が1つ減る。そして**唯一測定値がある経路**を採る
（11/12、数値は実行間で完全一致）。

**失うもの。** MDLの成熟した意味エンジン（リレーション、計算列、キューブ）を自分で持つことになる。
ただし**今必要なのは指標定義であって、それらではない** —— 必要になってから、そのとき再評価する
（COD-051）。

**倒れる方向（D6）。** 定義が古い・欠けていれば、C5により**生成されない**。C6により、
照合できなければ**数値が出ない**。いずれも閉じる側。

**残る宿題。** 定義層の実装（`QUERY_POLICY` の発展形）。
GA4以外のデータソースでは MDL の制約が当てはまらない可能性があり、**そのときは再評価**してよい
（このADRはGA4での実測に基づく）。

## 検討した代替案

**A. 顧客に平坦化ビューを作ってもらう。** D1を維持でき、D6の倒れ方も正しく、ビューは顧客の資産にも
なる。**却下の決め手は保守工数が顧客数に比例すること**（D3の再発）と、**壊れても直せないこと**。
なお本ADRの起草時、著者は一度この案を支持したが、保守工数の勘定が甘かったため撤回した。

**B. こちらが書き込み権限を得てビューを作る。** 一括更新できるのは利点だが、
**D1の読み取り専用性を失い、権限が放置されれば開く側に倒れる**。
オーナーが「アクセス制御は一番重要な設計の要」と置いた項目を、他で取り返せない形で削る。

**D. WrenAIを全面採用する。** 最速だが、GA4を表現できない問題が残り、さらに
**BigQueryコネクタがSA鍵を要求する**ためD1が消える。RLAC/CLACも公開文書に記載がなく、
**文書化されていない制御に境界を預けられない**（D6）。
